AQI Forecast: how the whole project works

    The system predicts PM2.5 (tiny dust particles) and the AQI (Air Quality Index, a 0–500 health score) for the next hour and the next 24 hours in eight Indian cities. It fetches fresh data every hour, grades its own past forecasts, retrains every day, and only swaps in a new model if it is truly better.

    Think of a restaurant kitchen that stays open: ingredients arrive hourly, every dish is tasted afterwards, and a new recipe only goes on the menu after it beats the old one in a blind test.

    Honest limits. The air values come from Open-Meteo’s computer models, not from sensors at your street. OpenAQ ground stations are used to check how far off those values are. The forecasts are estimates with uncertainty bands.

    The big picture

    Three layers: data comes in, models are made and checked, and results are served to people. Training reads the DVC snapshot, so every model can be traced to the exact data behind it.

    The loops that run by themselves

    Hourly: collect, predict, score

    Each hour GitHub Actions fetches new readings (ingest.yml), makes forecasts with the live model, grades older forecasts against what really happened, and checks for drift (monitor.yml). If the rolling error stays above 1.3 times normal for 3 hourly checks, an extra retrain starts and a message is sent to your webhook.

    Daily: retrain, compare, promote or reject

    At 02:00 India time retrain.yml exports the data, builds time-split windows, trains a candidate, and runs the gate. A rejection is a normal outcome and changes nothing for users.

    From raw rows to a forecast

    The model reads the last 48 hours of 13 signals (PM2.5, PM10, weather, wind direction as sine and cosine, and time of day and year) plus a learned vector for the city. It writes 24 hours ahead as three lines: a low (10th percentile), middle (50th) and high (90th) guess. Eight times out of ten the real value should land between low and high.

    Illustration only, not real data. The band widens because far-ahead forecasts are less certain.

    Windows are split by time: oldest 70% trains, next 15% tunes, newest 15% tests. Windows that straddle a boundary are dropped, so no future information leaks into training. Scaling numbers come from the training part only.

    The promotion gate

    Both the candidate and the live model are scored on the same held-out test windows. The candidate is promoted only if every rule passes (thresholds live in params.yaml).

    On promotion the ONNX file and scaler are stored in the database and the old model is archived. python -m src.models.rollback puts the previous one back.

    The “Explain this forecast” button

    The LSTM owns the number. Qwen (through ChatGroq) only narrates it, and a guard checks the words.

    If the AI text contains any number that was not in the data, or the AI service is unavailable, the app shows a plain template sentence instead. Requests are rate-limited and cached to protect the free quota.

    Checking against real stations (OpenAQ)

    Once a day, nearby PM2.5 stations are averaged per hour and compared with the model-based values we hold for the same hours. The Model health page shows the average gap, bias and correlation per city. This only measures trust. It never trains the model.

    What happens when someone opens a city page

    The browser loads the static React site from Vercel. The site calls the Render API, which reads the last 48 hours from Supabase, runs the ONNX model in memory, and returns percentile values converted to AQI. Responses are cached for a minute.

    Database tables

    Relations: a city has many observations, forecasts and ground_truth rows. Each forecast names its model_version, which links to model_runs and its stored artifact. scores join a forecast to the observation for its target hour. Row level security is on, and the app reaches Postgres directly.
